# T2 solution: block size one

Try the task first: [YOUR-TURN.md](../YOUR-TURN.md#t2-block-size-one).

## Answer

With the default block size, 10 new links moved the counter by **at most 3,000** (one trip per
replica that needed ids, 1,000 each). With block size 1, 10 links moved it by **exactly 10,000**:
ten trips, one per link, and each trip advanced the counter by 1,000.

## Why it works

A replica asks Postgres for a block with `nextval('link_id_blocks')`. The sequence is declared
`INCREMENT BY 1000` in [init.sql](../system/db/init.sql), so every trip moves the counter by
1,000 whatever the block size. At the default size a replica uses all 1,000 ids of a trip before
it asks again. At block size 1 it uses one id of each trip and throws the other 999 away, so you
pay twice: one database trip per link, **and** the ids run out 1,000 times faster. Part 1's table
shows the trip count: 100,000 trips for 100,000 links at one id per trip, against 100 with blocks
of 1,000. The lesson: a block size only makes sense together with the step of the counter that
hands the blocks out.

## What the check should show

```
counter after 10 links, block_size 1:     moved 10,000
counter after 10 links, default 1000:     moved 3,000      (1 to 3 trips, one per replica that was asked)
```

The checker applies `{"cache": false, "block_size": 1}`, makes 10 links and reads
`last_value`, then resets and does the same, and requires 10,000 and a value from 1,000 to
3,000. The exact default number depends on how the 10 links were spread over the replicas.
