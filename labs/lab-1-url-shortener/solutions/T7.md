# T7 solution: the clicks that vanish

Try the task first: [YOUR-TURN.md](../YOUR-TURN.md#t7-the-clicks-that-vanish). The fixed file is
[t7_solution.py](t7_solution.py).

## Answer

`step` read a batch, tried to write it, and when the write failed the batch was simply gone: it
lived in a local variable, and the queue never hands an event out twice. Keep the batch, and on
the next call try that same batch before reading a new one:

```python
batch = self._failed or await self._queue.consume(BATCH, WAIT_MS)
...
self._failed = batch  # remember it until it is safely counted
await self._store.add_clicks(...)
await self._queue.ack(batch.receipts)
self._failed = None  # only now is it safe to forget
```

## Why it works

The loop that calls `step` catches the error and calls it again a second later. Without the
`_failed` memory the second call reads *new* events and the failed batch is forgotten: in the
test, 1,200 clicks and two failed tries lose two batches of 500, so **only 200 are counted**. With
it, the failed batch is retried first and all 1,200 are counted. The acknowledgement still comes
after the write, so a crash between the two (the worker dies after the database accepted the batch
and before the queue was told) means the batch is delivered again and counted twice: **at least
once**, which is the promise for a click counter. Counting zero times is the one thing not
allowed.

Part 3 met this bug for real: 1,001 clicks were never counted after Postgres came back. The real
code is [ClickCounter](../system/shortener/src/shortener/worker.py#L27) and it has the same fix.
