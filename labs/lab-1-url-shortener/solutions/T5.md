# T5 solution: the link that exists but answers 404

Try the task first: [YOUR-TURN.md](../YOUR-TURN.md#t5-the-link-that-exists-but-answers-404). The
fixed file is [t5_solution.py](t5_solution.py).

## Answer

`make_link` saved the link but never told the cache. The fix is one line, **after** the
create succeeded:

```python
async def make_link(store, cache, code, url) -> None:
    if not await store.create(code, url):
        raise AliasTaken(code)
    await cache.set(code, url)
```

## Why it works

When someone opens `/launch` before it exists, the read path asks the store, finds nothing and
caches "does not exist" for 30 seconds (that is what stops someone scanning random codes from
hammering the database). If the link is then created and the cache is not told, the next opens
find the cached "does not exist" and answer 404 for up to 30 seconds, although the link is in the
database. Writing the real URL into the cache replaces the stale answer, and it also warms the
cache for the first click, which often comes seconds later.

The write has to come after the check that the create worked. If you put `cache.set` first, a
second person asking for a name that is taken would overwrite the first owner's cached URL with
theirs. The database would still say the first owner owns it, and the cache would send everyone
to the second person's page for an hour. That is the second test. The real API does it in the same
order: [create_link](../system/shortener/src/shortener/api.py#L112-L131).
