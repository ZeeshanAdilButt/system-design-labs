# T6 solution: stop the worker

Try the task first: [YOUR-TURN.md](../YOUR-TURN.md#t6-stop-the-worker).

## Answer

- **Failed redirects:** none. Redirects never wait for the worker.
- **Clicks waiting:** all of them, about **1,000** after 1,000 redirects (the ruler's last line).
- **Catching up:** within a second or two of the worker starting again, `click_backlog` is 0. The worker
  reads up to 500 events at a time and writes each batch to Postgres in one statement, so a
  thousand clicks take a couple of batches.

## Why it works

A redirect answers first and only then drops a click event on the queue (a Redis stream). The
worker reads the queue and adds the clicks up in the database in batches. Stopping the worker
stops the counting and nothing else, and the events wait in Redis until it is back. That is why
the clicks go through a queue instead of an `UPDATE` inside the redirect: if each redirect wrote
its click to the database before answering (`scenario.py apply '{"queue": false}'`), a slow or
dead database would make every redirect slow, and the worker being down would not be an option at
all. The price of the queue is that a click is counted a moment later, and that the events live in
Redis (part 3's Redis scenario counts what that costs).

## What the check should show

```
docker compose ... stop worker
redirect_timer.py --requests 1000   ->   failed: 0, clicks waiting in the queue: 1,000
docker compose ... start worker
curl .../api/stats                  ->   "click_backlog": 0   after a few seconds
```

The checker reports: `worker stopped: 0 failed, 1,000 clicks waiting after 1,000 redirects;
drained 0.5 s after it restarted`. It requires 0 failures, at least 900 clicks waiting, and an
empty queue within 30 seconds of the restart.
