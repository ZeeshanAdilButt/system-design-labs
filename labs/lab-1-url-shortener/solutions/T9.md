# T9 solution: a breaker that sends one scout

Try the task first: [YOUR-TURN.md](../YOUR-TURN.md#t9-a-breaker-that-sends-one-scout). The finished
file is [t9_solution.py](t9_solution.py).

## Answer

Add two flags: `_tripped` (set at the first failure, cleared when a scout succeeds) and
`_probing` (true while the scout is out). One helper, `_try`, now runs every Redis call:

1. Inside the cooldown: skip Redis.
2. Closed (never tripped, or recovered): call Redis.
3. Tripped, cooldown over, nobody testing: this request becomes the scout. Mark it and call Redis.
4. Tripped, cooldown over, a scout already out: skip Redis, like everyone else.
5. When the scout finishes: success closes the breaker, failure opens it again for a cooldown.
   Either way the scout flag is released in a `finally`, even for an unexpected error.

`get`, `set` and `ping` all go through `_try`, so none of them can pile on while the scout is out.

## Why it works

In the old breaker the cooldown ended at an instant, and every request in flight at that instant
saw "available" and went to Redis. With Redis still down, each of them waited for the socket
timeout (a quarter of a second): that is the 252.7 ms p99 part 3 measured. The new breaker has
a third state between open and closed, **half-open**: exactly one request tests, the rest keep
being served from the database. The scout may still pay the quarter second once per cooldown, but
the other nineteen do not.

The detail that matters is releasing the scout flag on every path. If a scout failed with an
error that is not a Redis error and the flag stayed set, nobody could ever test again and Redis
would be skipped forever after it came back.
