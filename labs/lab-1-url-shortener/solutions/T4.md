# T4 solution: switch the cache off

Try the task first: [YOUR-TURN.md](../YOUR-TURN.md#t4-switch-the-cache-off).

## Answer

- **How many redirects reach Postgres?** With the cache on: none (the ruler's links are cached
  when they are created, so it is 0 of 2,000; links that were not cached would be read from the
  database once each). With the cache off: **all 2,000**. That is the `answered from the cache`
  line: 100% against 0%.
- **The typical wait.** On a laptop with an idle database next to the API, the difference is
  small, from no difference to about 1.5x, and often **smaller than the run-to-run noise**. Part
  2's 2.1 ms against 3.3 ms was measured with one request at a time, and a busy machine buries it.
- **The slow wait (p99).** Even noisier. It jumps from run to run, in either direction.

## Why it works

What a cache reliably buys is **protection for the database**, not a dramatic win on every
request. A Postgres primary-key lookup on a small hot table is already fast, so on its own it
barely loses to Redis. What it cannot do is serve thousands of those lookups for the price of
none: each one takes a connection from a small pool, and when many arrive together they queue.
Part 2's under-load table (15 ms against 6 ms at the median, 68 ms against 17 ms at p99) shows
that effect when the machine has the spare capacity to show it. The cache also keeps the read
path alive when the database is not (part 3 and T8). If you saw a clear p50 gap you were lucky
with the noise. If you did not, your reading is correct too, and the right conclusion is that on
this machine a gap smaller than the spread between identical runs cannot be called a result.

## What the check should show

The checker measures 1,500 redirects with the cache on and with it off (16 in flight):

```
cache off: 0% cached, p50 9.2 ms, p99 31.5 ms | cache on: 100% cached, p50 9.7 ms, p99 124.8 ms
```

Only the shares and the failure count are judged (0% against above 95%, no failures). The waits
are printed and, as that run shows, can even come out the "wrong" way round. Ten more runs at 16
in flight on the same machine gave p50 values between 5 and 13 ms in both settings.
