# T8 solution: a circuit breaker for the database

Try the task first: [YOUR-TURN.md](../YOUR-TURN.md#t8-a-circuit-breaker-for-the-database). The
finished file is [t8_solution.py](t8_solution.py).

## Answer

`_guard` keeps two things: when the breaker last opened (or `None` when it is closed) and whether
a test call is out.

- Closed: call the store. If it raises, remember the time and re-raise (the caller still sees the
  real error, once).
- Open and inside the cooldown: raise `StoreUnavailable` at once without calling the store.
- Open and past the cooldown: let one call through as the test (and mark it, so a second caller
  arriving meanwhile is turned away). If it works, close. If it fails, open again.

The test marker is cleared in a `finally`, so a test call that is cancelled cannot leave the
breaker stuck.

## Why it works

The 2 seconds are the time asyncpg waits for a database that is not answering. Nothing about the
second request makes the database more likely to answer than the first one did, so waiting again
is pure cost. The breaker turns "ask and wait" into "do not ask for a moment". Because the API
already turns any exception from the store into a `503`, the wrapper needs no change anywhere
else. One breaker per replica is enough: each replica learns on its own.

The cost is the same as for the cache breaker: a short blind spot after the database returns (up
to one cooldown), and the one unlucky request that is the test pays the full wait. That is why the
test call is a single request and not everybody (T9 does the same for Redis).

**On the real stack (optional step, checked by hand once).** The finished file copied to
`system/shortener/src/shortener/breaker.py`, and the store in `build_store` wrapped as
`return BreakerStore(await PostgresStore.connect(...))`, with Postgres stopped and two quick
batches of requests for links that do not exist:

```
1: 503 in 2.007793s        first batch: one request per replica pays the wait
2: 503 in 2.006557s
3: 503 in 2.006734s
4: 503 in 0.007627s        second batch: instant 503s
5: 503 in 0.008839s
7: 503 in 0.005437s
8: 503 in 0.008097s
6: 503 in 2.007904s        a request that lands on a replica whose cooldown has just ended is the test call
9: 503 in 2.023991s
```

Sent one at a time with a pause, every request took about 2 seconds, because by the time the next
one arrived the 2 second cooldown had ended. A breaker only pays off when requests arrive faster
than its cooldown. After `docker compose start postgres`, the next two requests came back `404`
in 0.008 s: the breaker had closed again. This step is not part of `./verify`, because it needs a
rebuild of the images.
